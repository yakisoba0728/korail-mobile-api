## Rejected / non-bugs

One candidate finding was raised and re-checked this round; it **did not survive**. Several additional observations across groups are recorded here for completeness because they are **not** provable divergences from what the server sends/accepts.

1. **DynaPath token `rt` hardcoded to `"0"`** — `src/korail_mobile_api/dynapath.py:303` vs `analysis/jadx/sources/B/C1229b.java:119-127` (`rt`=delta list) with `C1229b.java:76-91` (delta calc) and `DynaPathMobileSDK.java:33-36` (`a(now)` called before `a()`). The divergence is factually real at ground truth: `DynaPathMobileSDK.generate()` calls `c1229b.a(System.currentTimeMillis())` — which appends a delta and sets `ts` — **before** building the token, so on the very first request `rt = [now − app_start_ts]` (a positive value) and on later requests it grows to up to **5** real inter-request deltas, emitted as an **array**; our stateless client always emits a single literal `"rt":"0"`. **Rejected as a non-bug** (LOW / effectively benign): (1) it is intentional and test-locked — `test_token_settings_do_not_accept_request_history` and `test_dynapath_generator_has_no_cross_request_state` assert the settings reject `recent_request_deltas` and the generator is stateless, and `test_http_generates_independent_fixed_rt_tokens_across_requests` pins independent per-request tokens; (2) it is proven server-accepted — the battle-tested `srtgo/ktx.py:153` sends `rt=0` successfully, and `test_generate_dynapath_token_matches_successful_fixed_rt_reference` pins a reference token with `rt=0` captured from a **successful** live interaction, so the server does not validate `rt` timing; (3) `rt` is inherently non-deterministic entropy the server cannot check for an exact value. The finding itself rates it LOW and gates flagging on a condition ("only if the DynaPath server ever validates `rt` timing plausibility") that `srtgo` disproves, and its own suggested resolution concedes keeping `rt=0` is acceptable. The suggested fix (seed `rt` with a positive `ts − app_start_ts` delta and keep a ≤5 rolling window) would reintroduce exactly the cross-request state the maintainers deliberately removed and the tests forbid — a regression against a validated design, not a correction. *Recommendation: keep `rt="0"`, but document it as a deliberate stateless approximation and track the divergence.*

2. **Related DynaPath observation — `dyn_key` random-char alphabet 36 vs 62** — `src/korail_mobile_api/dynapath.py:19` (36 chars: uppercase + digits) vs `analysis/jadx/sources/B/C1229b.java:164` (62 chars: lowercase + uppercase + digits). ~~**Not a bug:** the value is random entropy the server cannot predict or validate, and `srtgo` uses the same 36-char set and works. Non-actionable.~~ **Overturned 2026-07-26 and fixed** (`fix/apk-fidelity`): `dynapath.py:19` now uses the app's 62-character set. Both premises held but the conclusion did not follow: `rand` is embedded in `dyn_key` and therefore **transmitted** inside `encoded_key`, so the restricted alphabet is observable, and "srtgo does it too" is an argument that srtgo is fingerprintable, not that we should be. Whether the server acts on it remains UNVERIFIED; matching the app costs nothing.

3. **Common-station over-strict readers / stale fixture** — `parse_station_info_response` requires non-empty `map_version` (`parsers.py:439-444`) and `parse_station_data_response` requires non-empty `stn_cd`/`stn_nm` (`parsers.py:282-288`) while the GSON DAOs tolerate null; `parse_train_calendar_response` requires `hldyDvCd` present (`parsers.py:504-508`), mirroring the app's own NPE in `isHoliday()` (`TrainCalendarDao.java:60-62`). `client.get_common_code('')` sends `code=['']` (used by `live.py:102` smoke test) — a user-convenience wrapper, not an app-mimicking call. `tests/fixtures/train_calendar.json` uses the model alias key `days` rather than the wire key `runningCalendar`, but it is a stale model-shape fixture **not** fed to the wire parser (the wire fixture `raw_typed_train_calendar.json` correctly uses `runningCalendar`), so no runtime effect. **None provable against a real response.**

4. **Search-schedule semantic/coverage notes** — the app derives `txtTotPsgCnt`/`totPsgCnt` for the car-list and residual-seat reads from the echoed `trainInfo.getTotPsgCnt()` of the selected row (`x4/b.java:22`), whereas `build_seat_car_form`/`build_seat_inventory_form` take a caller-supplied `passenger_count` (default 1); both emit a valid integer field and the caller controls the value — a semantic difference, not a wire divergence. `ScheduleViewSpecial`/`getRsvProductInquiry` is present but unwired (route only in `DYNAPATH_ALLOWLIST_PATHS`, `constants.py:40`, absent from `KORAIL_READ_ONLY_ROUTES`); if wired it would be blocked by `assert_read_only_route` — incomplete, not divergent. **Not filed.**

5. **Seat-fare-traininfo strictness + comment nit** — `parse_train_schedule_response` requires `runDt1` non-empty and each `dlayList` row's `stopStnNm` non-empty and `dlayList` itself required; `parse_transfer_station_list_response` requires `chtnRsStnCd` non-empty (the empty-code `전체` row is client-synthesized via `TrainSelectStationDao.getAllTransferStationInfo`, not server-sent). A stale code comment near `parsers.py:730` says "msgCont stay required" but the code correctly parses `msgCont` as optional — comment-only, no wire/parse impact. **None provable against a real response.**

6. **Ticket-reservation-read completeness gaps** — these are optional **display** fields the parser does not surface as typed attributes, but the untouched server object is retained on each item's `.raw`, so no data is lost or mis-parsed: `parse_ticket_receipt_response` omits the `cash_rcet_info` list (`ReceiptDao.CashReceiptInfo`: `h_apv_mtd_nm`, `h_athn_dmn_rcgn_no`, `h_cash_rcet_apv_no`, `h_cash_rcet_txn_dv_cd`, `h_tot_apv_amt`); `parse_reservation_history_response` omits `h_ntisu_lmt_dt`/`h_ntisu_lmt_tm` (purchase deadline), `h_ntisu_psb_dt`, `h_ise_psb_tm`, and `h_payment_msg` from `TicketRsvHistoryDao.TrainInfo` (which `srtgo` surfaces as `buy_limit_date`/`buy_limit_time`). Consider adding these if downstream consumers need the payment deadline without touching `.raw`. **Not divergences.**

7. **Account-pass-maas-limousine theoretical-robustness notes** — `parse_limousine_seat_inventory_response` uses `_required_list` for `seatList` (`limousine_parsers.py:180`) while the sibling schedule parser uses tolerant `_nullable_list`; the DAO types `seatList` as a nullable `ArrayList`, but no evidence the server returns `SUCC`+null `seatList`, so only a theoretical inconsistency. `parse_reservation_history_response` classifies `P100` as a non-fatal empty code (`read_parsers.py:1084`); `P100` is a server-generated code that appears nowhere in the decompile and cannot be confirmed/refuted from the client bytecode (worst case, harmless dead-defensive code, since the `SUCC`-empty path is handled separately). Both merit a fixture-backed live capture to settle. **Neither is a provable protocol bug.**

8. **Safety-transport coverage notes** — `copt.gdMenuLt.do` models only the base `{Device, Version}` menu-read; the 5-field MaaS-reservation shape (`Device`, `Version`, `pnrNo`, `tkRetNo`, `addSrvReqNo`) is unsupported, but that path is a MaaS add-service context outside read scope. Several set-validated routes (e.g. `LimousineScheduleView`) mark all app `@Field`s required, so the client always sends the full set even where the app might null-drop an unselected field — stricter-than-app, not wrong-data. **Not divergences.**

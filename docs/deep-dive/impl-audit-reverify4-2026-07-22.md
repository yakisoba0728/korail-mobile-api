# Korail Client Implementation Audit — Re-verify (Round 4) — 2026-07-22

**Target app:** `com.korail.talk` v6.5.0 (decompiled ground truth under `analysis/jadx` + `analysis/apktool`)
**Under audit:** the read-only Python client in `src/korail_mobile_api/`
**Author:** FABLE
**Ground-truth rule:** the decompiled Korail app is authoritative. Where a client test bakes in a divergence, the test is treated as wrong, not the app; where `srtgo` / `srtgo_plus` diverges from the decompile, the decompile wins.

## Overview

This is the **fourth adversarial re-verify** pass (2026-07-22) over the scoped sub-audits — auth/session/crypto, common-station, search-schedule, seat-fare-traininfo, ticket-reservation-read, account-pass-maas-limousine, and safety-transport. Every candidate divergence was re-checked against the decompiled Retrofit DAOs (and, where relevant, apktool smali / fixtures / the `srtgo_plus` reference) before being counted. Findings that did **not** survive that check are listed under [Rejected / non-bugs](#rejected--non-bugs) and are **not** counted as real. Each surviving finding carries both-sides `file:line` citations: where our client diverges, and where the app proves the correct behavior.

**6 divergences survived verification: 2 Medium, 4 Low, 0 High.** None is a wrong route, wrong HTTP method, wrong envelope, or a missing-required outbound field. Both Mediums are *over-rejection* defects — the parser hard-fails a response the app renders fine (a car with no special-seat attributes; an empty pass-schedule query). The four Lows are peripheral: an empty-valued param where the app omits the field, and three over-strict response readers (a required-string field the app null-tolerates, and two numeric readers narrower than Gson's string→int coercion).

## Detailed findings

### RV4-01 — seat-car parser hard-fails a car with no special-seat attributes (Medium)

- **Our ref:** `src/korail_mobile_api/parsers.py:894` (`seatAttInfos` via `_inventory_required_list`).
- **Ground-truth ref:** `analysis/jadx/sources/com/korail/talk/network/dao/research/SearchCarListDao.java:19` (nullable `List<SeatAttInfo> seatAttInfos`); consumer null-guard at `analysis/jadx/sources/com/korail/talk/ui/seat/SeatSearchActivity.java:254`.

`SearchCarListDao.CarInfo.seatAttInfos` is a plain nullable Gson list. The app never assumes it is populated: `SeatSearchActivity.C0804d` runs `C0804d.isNull(seatAttInfoList) || seatAttInfoList.size() == 0` before touching it, so a car row that carries **no** special-seat attributes (a normal car) is rendered without incident. Our client instead routes the field through `_inventory_required_list` and raises `KorailProtocolError`, aborting the whole `getCarList` read. Empty list `[]` parses correctly; only `null`/absent over-rejects. The over-strictness is pinned by `tests/test_seat_inventory_reads.py:503-505`, which asserts that popping `seatAttInfos` raises — so the fix must also relax that test.

This is the same class as the (unreported, effectively-always-present) core `int` fields `h_srcar_no`/`h_rest_seat_cnt`/`layout_type`/`seat_remain_count`/`seat_total_count`, but unlike those, `seatAttInfos` is genuinely optional in normal traffic (any car without special seats), which is why it is counted.

**Fix.** Default to an empty attributes tuple when `seatAttInfos` is null/absent; raise only when present-but-not-a-list. Drop the popped-`seatAttInfos` case from the malformed-container test.

### RV4-02 — pass-schedule parser throws on a legitimate empty query (Medium)

- **Our ref:** `src/korail_mobile_api/read_parsers.py:1374` (`_validate_envelope` with no `accepted_empty_codes`, then `strResult == "SUCC"` required).
- **Ground-truth ref:** `analysis/jadx/sources/com/korail/talk/ui/inquiry/CommutationInquiryActivity.java:182` (`commRsvInquiryDao.setErrorMsgCdNotShowDialog("WRG000000")`), dispatched via `BaseActivity.onIntegrationResult` / `l4.h`.

The app tags the pass-schedule DAO (`CommRsvInquiryDao` → `passScheduleInfoList`) with `setErrorMsgCdNotShowDialog("WRG000000")`. The result dispatcher builds an error object only when `strResult == FAIL || h_msg_cd == "WRC000288"`, and consults the no-dialog code list only on that path — so an empty pass-schedule inquiry comes back `strResult=FAIL` + `h_msg_cd="WRG000000"` and is treated by the app as "no schedules", suppressing the error dialog and rendering an empty list. Our parser has no `accepted_empty_codes` and demands `SUCC`, so it raises `KorailAppError` on exactly this case.

The sibling `parse_discount_coupon_response` (`read_parsers.py:689`) already tolerates `WRG000000` as an empty code — even though the app does **not** register that code for the coupon DAO — so the codebase's own convention runs the opposite way from where the decompile actually warrants it.

**Fix.** `_validate_envelope(..., accepted_empty_codes=frozenset({"WRG000000"}))`; on the empty return, hand back a `PassScheduleResponse` with empty `schedules`, mirroring the coupon parser.

### RV4-03 — empty-valued `txtGdNo`/`gdNo` sent where the app omits the field (Low)

- **Our ref:** `src/korail_mobile_api/payloads.py:165` (`_resolved_goods_no → ""`).
- **Ground-truth ref:** `analysis/jadx/sources/x4/b.java:23` (`getSearchRequest` forwards `trainInfo.getTxtGdNo()` verbatim); `analysis/jadx/sources/.../research/ResearchService.java:37,59` (`@Field("txtGdNo")` / `@Field("gdNo")`).

`SeatSearchRequest.getTxtGdNo()` returns null for a normal non-goods train, and Retrofit drops null `@Field` params — so for standard KTX/무궁화 seat reads the app sends **no** `txtGdNo`/`gdNo` at all. Our builders send the key with an empty value. The in-code comment at `payloads.py:123-124` justifying this ("matching the empty txtGdNo the app sends for non-goods trains") is factually incorrect. Server impact is minor because empty is generally treated as absent, hence Low.

**Fix.** Omit `txtGdNo`/`gdNo` when `goods_no` is falsy (same `del form[key]` pattern already used for `txtSeatAttCd`/`seatAttCd`), and correct the comment.

### RV4-04 — `trnNo1` over-required in the actualTrainSchedule parser (Low)

- **Our ref:** `src/korail_mobile_api/parsers.py:727` (`_typed_required_string(non_empty=True)`).
- **Ground-truth ref:** `analysis/jadx/sources/com/korail/talk/ui/web/TrainServiceInfoWebViewActivity.java:200` (`if (!N.isNull(tranNo1))`).

The app's web-view consumer null-guards `tranNo1`, omitting the train number from the header when it is null; our parser rejects the whole response. `runDt1`/`msgCont` are consumed unguarded, so keeping those required is correct — only `trnNo1` is over-strict. A valid `actualTrainSchedule` query echoes the train number, so this rarely fires, hence Low.

**Fix.** Make `train_no` (`trnNo1`) optional in `parse_train_schedule_response`.

### RV4-05 — `h_psg_num` requires a native int the wire delivers as a quoted string (Low, latent)

- **Our ref:** `src/korail_mobile_api/read_parsers.py:1654` (`if type(passenger_count) is not int: raise`).
- **Ground-truth ref:** `analysis/jadx/sources/com/korail/talk/network/dao/trainsInfo/TourTrainInfoDao.java:14` (`private int h_psg_num`); wire-type proof in `tests/fixtures/seat_car_list_live_shape.json` (`h_srcar_no`/`h_rest_seat_cnt` as strings) exercised by `tests/test_seat_inventory_reads.py:395`.

`h_`-prefixed integers arrive quoted on the wire; the seat parsers were hardened to accept ASCII-decimal strings (`_inventory_integer_value`, `parsers.py:814-838`) for exactly this reason. `parse_tour_train_info_response` was never hardened, so a real `h_psg_num:"2"` raises instead of parsing `2`. The success fixture (`tour_train_info_success.json`) uses a native int, masking the gap in unit tests. The endpoint is intentionally unwired today (no `get_tour_train_info` client method; absence asserted by `test_next_account_reads.py:246`) — latent until someone wires transport up, hence Low.

**Fix.** Coerce `h_psg_num` with the same int-or-ASCII-decimal-string helper the seat parsers use; keep rejecting non-numeric/null.

### RV4-06 — strict JSON-int on `rsvCnt`/`scarNo` narrower than the app's Gson coercion (Low)

- **Our ref:** `src/korail_mobile_api/read_parsers.py:1921` (`_required_json_integer` for `rsvCnt`; same pattern for seat `scarNo`).
- **Ground-truth ref:** `analysis/jadx/sources/com/korail/talk/network/dao/ticket/TicketDuplicationCheckDao.java` (`DuplicationCheckResponse.rsvCnt : int`); `PbpAcepSpecDao.java` (`Seat.scarNo : int`).

Both fields are Java `int` deserialized by Gson, whose `JsonReader.nextInt()` coerces a quoted numeric string into the int — so the app accepts both `"rsvCnt":0` and `"rsvCnt":"0"`. `_required_json_integer` accepts only the numeric form. The same KORAIL numeric-as-string pattern is already defended in the receipt parser via the lenient `_optional_integer` (the `ticket_receipt` fixture even mixes `1` and `"2"` for the same int-declared DAO fields). If the live server returns these as strings, our client raises where the app succeeds. Not confirmed against a captured real response, so the trigger depends on the actual wire type — hence Low.

**Fix.** Read `rsvCnt`/`scarNo` with `_optional_integer` (or a `_required` variant that accepts ASCII-decimal strings), matching the receipt fields and Gson's string→int coercion.

## Rejected / non-bugs

Two candidate findings were re-checked and **did not survive** — they are not counted as real divergences.

1. **DynaPath token `rt` hardcoded to `"0"`** — `src/korail_mobile_api/dynapath.py:303` vs `analysis/jadx/sources/B/C1229b.java:80,126` (+ `DynaPathMobileSDK.java:34`). The divergence is factually real at ground truth: the app computes `rt = ts - it` on the first request (`C1229b.a(long)` :80) and inter-request deltas from a max-5 deque (:126), emitting an **array**, whereas our client emits a constant single `"rt":"0"`. **Rejected as a non-bug**: this is an intentional, tested, live-validated *stateless* design decision, not a defect. (1) `DynapathTokenSettings` deliberately has **no** request-history field, and `test_token_settings_do_not_accept_request_history` (`tests/test_dynapath.py:57`) asserts passing `recent_request_deltas` raises `TypeError`; (2) `test_dynapath_generator_has_no_cross_request_state` (:140) asserts the generator is stateless; (3) `test_generate_dynapath_token_matches_successful_fixed_rt_reference` (:69) pins a reference token with `rt=0` captured from a **successful** live-server interaction — empirical evidence the real Korail backend accepts `rt=0`, refuting the speculative "anti-automation red flag" concern; (4) the finding itself concedes "real-world impact may be nil." The suggested fix (compute `rt` from elapsed time / maintain a delta deque) would reintroduce the exact cross-request state the maintainers deliberately removed and the tests explicitly forbid — a regression against a validated design, not a correction. (Related minor note, also not a bug: `constants.KORAIL_DEFAULT_OS_VERSION='35'` conflates the Android SDK int with `Build.VERSION.RELEASE`; the built-in generator ignores it and uses the required `DynapathTokenSettings.os_version`, so no wrong value is emitted by the default path, though a custom `token_provider` trusting `context.os_version` would emit `'35'`. Consider aligning the default to a RELEASE string.)

2. **`copt.gdMenuLt.do` exact-field contract is a subset of the DAO** — `src/korail_mobile_api/safety.py:189-191` vs `analysis/jadx/sources/com/korail/talk/network/dao/common/CommonService.java:46-48` (+ `MaasMenuListDao.java` two-branch `executeDao`). The DAO `getMaasMenuList` declares 5 `@Field`s `{Device, Version, pnrNo, tkRetNo, addSrvReqNo}`; `executeDao` branch 1 calls `getMaasMenuList(device, version, null, null, null)` → after Retrofit null-omit sends only `{Device, Version}`, branch 2 adds the pnr fields. **Rejected as a non-bug**: `build_maas_menu_form` (`payloads.py:337-341`) emits exactly `{Device, Version}` and `get_maas_menu_list` (`client.py:914-925`) uses `include_common=False`; there is **no** client code path that builds the pnrNo-scoped variant, so the registered contract exactly matches what the client actually sends (DAO branch 1) — no wrong-send, no missing-required field, no spurious field. The finding's justifying premise ("every other allowlisted route's field set exactly matches its DAO") is **false**: `gift.gdLst.do` (`GifticketService.java:19`) declares 11 `@Field`s but its `KORAIL_EXACT_REQUEST_FIELDS` entry (`safety.py:371-382`) registers only 8, deliberately omitting `qryNumNext`/`fllwQryFlg`/`trnOprBzDvCd`. The codebase intentionally registers the fields the client **sends**, not the DAO superset, so `copt.gdMenuLt.do` is consistent and correct.

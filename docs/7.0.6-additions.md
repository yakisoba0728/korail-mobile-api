# 7.0.6 추가 기능 구현

**현재 상태 (2.0.0).** `v7_contract_data.py`의 `CONTRACT_ROWS`는 정확히
2행이다: `NetworkApi.verifyOnlineRefunds`(조회)와
`NetworkApi.executeOnlineRefunds`(상태 변경). `client.v7.call()`은 이 두
이름 밖의 어떤 메서드도 부르지 못한다 — 레지스트리에 없는 이름은
`KorailProtocolError`다. `client.v7`은 앱의 다른 호출로 가는 일반 통로가
아니다. 아래 문서 본문은 이 레지스트리가 117행이던 시절의 구현 기록이며,
그 시절 이후 무엇이 남고 무엇이 사라졌는지를 먼저 정리한다.

## 지금 남은 두 계약

| 메서드 | HTTP | 경로 | 분류 |
| --- | --- | --- | --- |
| `NetworkApi.verifyOnlineRefunds` | POST | `/classes/com.korail.mobile.refunds.verifyOnlineRefunds` | read (`KORAIL_READ_ONLY_ROUTES`) |
| `NetworkApi.executeOnlineRefunds` | POST | `/classes/com.korail.mobile.refunds.executeOnlineRefunds` | mutation, `refund` 범주 (`KORAIL_MUTATION_ROUTES` + `KORAIL_MUTATION_ROUTE_CATEGORIES`) |

둘 다 `NetworkApi`의 평범한 `@FieldMap` 폼 계약이다 — `@Body`도 `@QueryMap`도
아니다. 두 계약 모두 상위 API와 같은 `safety.py` 라우트 표를 거친다: read는
`KORAIL_READ_ONLY_ROUTES`의 원소여야 하고, mutation은
`KORAIL_MUTATION_ROUTES`의 원소이면서 `KORAIL_MUTATION_ROUTE_CATEGORIES`에
등록된 범주와 일치해야 한다. **동의 객체도 dry-run도 없다** — 세션이 있는
채로 `executeOnlineRefunds`를 부르면 그 순간 나간다. 실행은
`KorailClient.execute_station_ticket_refund`, 조회는
`KorailClient.verify_station_ticket_refund`다(둘 다 `client.py`).

정기권/패스 구매 계약 네 개(`NetworkApi.postPassReserve`,
`NetworkApi.postPassPayIssue`, `NetworkApi.passOtrReserve`,
`NetworkApi.postPassOtrPayIssue`)는 이 2행 레지스트리에 아예 없다. 설령
있었더라도 `call()`은 레지스트리를 찾아보기 **전에** 이름으로 무조건
거부한다(`v7.py`의 `_NEVER_SENT`, `KorailMutationNotAllowedError`). 이유는
`docs/MUTATION_HANDOFF.md`의 정기권 절에 있다.

```python
from korail_mobile_api import KorailClient, KorailMutationNotAllowedError

client = KorailClient()
try:
    client.v7.call("NetworkApi.postPassReserve", {})
except KorailMutationNotAllowedError as error:
    print(error)  # 정기권/패스 구매는 이름으로 항상 거부된다

try:
    client.v7.call("NetworkApi.getSearchMetaData", {"version": "7"})
except Exception as error:
    print(type(error).__name__, error)  # 레지스트리에 없는 이름은 KorailProtocolError
client.close()
```

이 예제는 로그인도 네트워크도 필요 없다 — 두 거부 모두 요청을 만들기 전에
일어난다. 반대로 세션이 있는 상태에서 레지스트리에 있는 이름(예:
`NetworkApi.executeOnlineRefunds`)을 부르면 그 순간 실제 요청이 나간다.

## 117행이던 시절의 구현 기록

아래는 이 레지스트리가 117행이었을 때의 구현 기록이다. 그때 연결됐던
메서드 대부분(정기권/패스 구매 네 개를 포함해)은 지금 레지스트리에 없고,
`client.v7.call()`로 부를 수 없다. 이 절 안에서 각주 없이 현재형으로 쓰인
문장은 전부 그 시절을 가리킨다.

7.0.6 APK의 Retrofit 주석에서 확인한 기존 허용 목록 밖의 고유 메서드 117개를
`KorailClient.v7.call()`로 연결했었다. 경로/HTTP 동사 고유 쌍은 112개였다.
같은 경로를 여러 메서드가 공유해도 메서드 이름, 어노테이션 입력형, 응답
모델명을 각각 보존했다. 원본과 대조 가능한 전체 목록은 그 시절의
`v7_contract_data.py`에 있었다(지금은 위의 2행으로 줄었다). 생성 근거였던
`analysis/reports/7.0.6-additions/methods.tsv`와
`analysis/reports/7.0.6-additions/input-models.tsv`는 이 저장소에 더는 없다.

| 경계 | 메서드 | 조회로 분류 | 동의가 필요한 상태 변경 |
| --- | ---: | ---: | ---: |
| KORAIL `NetworkApi` | 92 | 28 | 64 |
| 제휴 API 8개·별도 `PushService` | 25 | 24 | 1 |
| 합계 | **117** | **52** | **65** |

`GET product.ReservationCancel`과 `GET PushService.push.update`처럼 GET이지만
취소·갱신에 해당하는 계약은 상태 변경으로 다뤘다. 분명히 조회 또는 서버 쪽
변환으로 확인된 메서드만 조회로 분류했고, 불확실한 경우에는 메서드별 동의를
요구했다. dry-run 미리보기는 원시 wire key의 의미가 보호돼 있을 수 있어
값을 모두 가리고 키 이름과 반복 개수만 보여줬다. 메인 KORAIL 호출은 기존
`KorailHttpClient`의 세션 쿠키와 DynaPath 설정을 썼다. 제휴 API는 호출자가
각 인터페이스의 HTTPS origin을 주입해야 했으며, 인터페이스별 독립 클라이언트를
만들되 APK의 공유 CookieManager처럼 메인 클라이언트와 도메인 범위의 쿠키
저장소를 공유했다. `PushService`는 보호된 webHost origin을 호출자가
주입하되 APK처럼 메인 HTTP 클라이언트를 공유했다. **이 문단이 설명하는
제휴 API 클라이언트·PushService 연동은 지금 레지스트리에 남은 두 계약
어느 쪽에도 해당하지 않는다 — 둘 다 메인 `NetworkApi`이고,
`V7Gateway._client_for`는 지금 메인 클라이언트 하나만 돌려준다.**

당시 코드는 생성 데이터에서 조회로 표시된 `NetworkApi` 11개를 상태 변경 가능
계약으로 보수적으로 재분류했다. 비밀번호·포인트 인증 5개(`postDiscountCheck`,
`postInquiryIsMember`, `postLPotAthn`, `postXPointView`,
`postOkCashbagCertView`), 체크인·QR·회원 인증·결제 상태 확인 5개
(`postSelfCheckInInfo`, `postSelfCheckInPossible`,
`postLocalRailwayTravelQrAuth`, `postMemberVerify`, `paymentMassStatusIn`),
비회원 예약을 만드는 `postNonMemTicket`(응답 `ReservationOut`) 1개였다. 이
11개는 당시 `v7_contract_data.py`의 Retrofit 서명은 유지하고 실행 경계에서
메서드별 동의와 기본 dry-run을 요구했으며, 서버에는 전송한 적이 없었다.
**이 11개 이름은 지금 레지스트리에 없다 — 오늘 `client.v7.call()`로 부르면
`KorailProtocolError: unknown 7.0.6 method`다.**

폼의 반복 `@Field`는 문자열 목록으로 전달했다. Retrofit nullable 인자는
해당 키를 생략했다. `@FieldMap`과 `@QueryMap`은
APK DTO의 Python 속성명이 아니라 실제 wire key를 받았다. `@Body`는 JSON
object, `@Header`는 `headers=`로 별도 전달했다. `GreenCarDetailRequest`는
문자열 필드 2개, `CacheCheckRequest`는 문자열 맵 1개를 요구했다 — 둘 다 지금
레지스트리에 없는 계약이다. DTO가 상속하는 `Device`/`Version`/`Key`를
포함해야 하는 계약에서는 `include_common=True`를 선택할 수 있었다 — 이
옵션 자체는 지금도 `V7Gateway.call`에 남아 있고, 남은 두 계약이 모두
`NetworkApi`의 폼 계약이라 여전히 쓸 수 있다. APK의 보호 코드에 숨은
`lang`, Key/Version 새 기본값, 일부 직렬화 필드 이름은 임의로 채우지
않았다.

Android 내부의 자동 로그인, PIN, 생체인증, 로컬 레코드, 푸시 흐름은
`korail_mobile_api.android_features.AndroidFeatures`가 연결했다. **이 모듈은
저장소에서 완전히 제거됐다 — `src/korail_mobile_api/android_features.py`는
더는 존재하지 않고, `AndroidFeatures`도 `AndroidRecordStore` /
`AndroidCredentialCipher` / `AndroidBiometricGate` / `AndroidPushAdapter`도
이 패키지 어디에도 없다.** 아래는 그 모듈이 있었을 때 설명했던 내용을
있는 그대로 남긴 기록이다.

일반 로그인 자격증명은 호스트의 KeyStore 암호화로 저장했다. 자동 로그인은
저장된 `auto` 설정과 `inputFlag`를 재사용했다. 회원 로그인은 현재 고객번호가
일치해야 했으며 `LoginType.NONE`은 이 검사를 건너뛰었다. PIN은 6자리 숫자로
로컬 비교하며 오류 5회에서 잠기고 PIN 또는 생체 로그인 성공 시 오류 수를
초기화했다. 생체 자격증명은 BiometricPrompt에 묶인 호스트 키로 별도
봉인/해제했다. 로컬 기록은 APK Room의 18개 DAO 이름으로 분리했으며,
Preferences DataStore 2개와 메모리 DataStore 8개도 별도 namespace로
접근했다. 소셜 로그인 기록은 암호화 고객 ID와 로그인 수단 코드를 저장했다.
푸시 설정은 Android SmartAgent/FCM 호스트 어댑터와
`NetworkApi.postPushUpdate`/`PushService.pushUpdate` 계약으로 이어졌다 —
이 두 계약도 지금 레지스트리에 없다. 로그아웃은 서버 로그아웃을 호출하면서
저장 ID 설정을 유지하거나 지우고, 저장 비밀번호·자동 로그인 설정을
해제했다. 위젯과 고객 여행기록은 전체 행을 삭제하고 Push off로 바꿨다.
간편/소셜 로그인과 승차권 로컬 기록은 유지했다.

이 저장소는 Python 클라이언트여서 Android KeyStore, Room, BiometricPrompt,
FCM/SmartAgent 실행체를 담은 적이 없다. 이번 구현은 정적 APK 계약의 호출
형태와 로컬 상태 흐름을 다뤘다. Python 클라이언트의 실서버 로그인·조회·미결제
예약 및 취소 결과는 [7.0.6 실서버 검증](7.0.6-live-verification.md)에 기록했다.
이후 일반 승차권의 실카드 결제·전액 환불 한 건은 Python 클라이언트로
실서버에서 성공했다. 신규 V7 변경 계약과 Android 내부 호스트 실행은
실서버·단말에서 검증하지 않았다.

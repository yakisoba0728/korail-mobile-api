## 별도 실결제·전액 환불 왕복 — 2026-09-15

사용자가 승인한 카드로 2026-09-29(화) 서울→영등포 무궁화호 1인 일반석을
예약했다. 실서버 검색에서 예약 가능한 열차 10편과 최저 운임 표시 2,600원을
확인했고, 한 건의 예약 응답 금액과 독립 예약 상세 금액을 대조했다. 결제 금액
상한은 5,000원으로 고정했다. 실카드 결제 성공 후 새 승차권 참조로
`SelTicketInfo`와 `CommissionView`를 조회했다. 서버가 반환한 환불 가능 금액은
2,600원, 위약금은 0원이었다. 즉시 `RefundsRequest`를 실행해
`SUCC/IRT200277`을 받았다. 이어진 독립 세션 재조회에서 미결제 예약 0건,
활성 승차권 참조 0건을 확인했다. 카드사 청구·취소 반영 시점은 별도로 조회하지
않았으므로 이 검증은 코레일 서버의 결제·환불 수락과 계정 상태 확인까지다.

실행 전 실카드 왕복 스크립트의 오프라인 안전 검사 80개가 통과했다. 회원번호,
로그인·카드 비밀번호, 카드번호·유효기간·생년월일, 쿠키·PNR·승차권 참조,
원문 응답은 파일이나 출력에 남기지 않았다. 이 결과는 일반 승차권 결제·전액
환불 한 건에 한정되며, 아래 신규 V7 제휴·보상·부분 환불 계약을 검증하지 않는다.

## 코레일 API 환불 정산·MAAS 이력 후속 조회 — 2026-09-15

카드사 앱·웹은 사용자 요청에 따라 조회하지 않았다. 코레일 API만으로 새 환불
승차권의 구매이력 1건을 다시 찾고, 동일 참조로 `SelTicketInfo`와 `ReceiptInfo`를
조회했다. 세 호출 모두 `SUCC`였고 영수증 1건에는 결제 수령액 2,600원,
`h_crd_ret_amt` 카드 환불액 2,600원, 환불 위약금 0원,
`h_ret_rcvd_amt` 반환 수령액 2,600원이 기록되어 있었다. 코레일 서버에
카드 반환 정산이 반영된 것은 확인했지만 카드사 전산의 최종 취소 반영 여부는
이 API로 증명할 수 없다. 참조값·카드번호·승인번호·응답 원문은 출력하거나
저장하지 않았다.

처음에는 3개월 제한을 넘겨 요청 전 차단됐던 MAAS 이력을
`20260901`~`20260915`로 재조회했다. `SUCC`, 내역 0건이므로 이 조회 경로의
정상 응답은 확인했으며, 실제 내역이 있는 경우의 파싱은 아직 미검증이다.

## 보호된 입력을 제외한 남은 항목 재시도 — 2026-09-15

사용자가 보호된 7.0.6 상수·호스트·wire 기본값을 제외하고 남은 검증을 다시
요청했다. 별도 로그인 세션에서 실제 2026-09-29 서울→부산 검색 열차 10편과
정차역 7곳을 얻고, 그 열차의 실제 중간 정차역을 병합좌석 요청의
`selRsStnNm`로 보냈다. 응답은 `SUCC`, 열차 2편과 중간역 5곳이었다.
늦은 시각 직통 검색은 여전히 `SUCC`와 빈 목록이라 fallback이 일어나지
않았지만, 포항→목포와 진주→강릉 두 실제 여정에서는 공개 메서드
`search_trains_with_transfer_fallback`이 `TransferSearchResult`를 반환했다.
각각 환승 열차 8편·10편을 파싱했다. 이 메서드는 직통 `WRD000061`
예외에서만 환승으로 넘어가므로 해당 분기의 실서버 실행을 확인한 것이다.
직통 실패 원문은 저장하지 않았다.

같은 날짜의 다자녀 할인 대상은 다시 `WRC800029`로 거절됐다. 로그인 성공과
예약 가능한 열차 존재는 확인했지만 계정의 가족 등록 자격을 만들어낼 수는
없다. 입력 없는 V7 `NetworkApi.postSpecificDateData` 재조회는 `SUCC`였다.
운임 견적의 입석 열차 분류 코드는 실제 열차 정차역 조회에서 얻었지만,
검색 행과 응답 메타데이터의 상품번호는 비어 있었다. 현재 Python 빌더는
상품번호를 비워 보낼 수 없고, 7.0.6 APK의 상품번호 기본값은 보호되어
있으므로 임의 값을 만들어 전송하지 않았다.

전달 수령인 조회는 현재 활성 승차권이 없어서, 앞선 결제 왕복과 동일한
상한 5,000원·수수료 없는 미래 날짜로 새 일반 승차권 한 건을 2,600원에
발권한 뒤 진행했다. 새 승차권 상세의 `h_sale_dt`와 그 상세의 원표
창구·순번·반환 비밀번호를 조합해 읽기 요청을 보냈다. 서버는 기존
`ERB000001` 입력 검증 오류 대신 `IRZ000005`(조회할 자료가 없음)를
반환했다. 일반 승차권에 전달 수령인이 없다는 해석과 일치하지만,
전달받은 승차권의 수령인 있음 응답 파싱 성공이나 자료 없음의 단일 원인을
증명하지는 않는다. 환불 견적
2,600원·위약금 0원을 확인하고 즉시 전액 환불 `SUCC/IRT200277`을 받았다.
독립 로그인 재조회에서 미결제 예약 0건과 활성 승차권 0건이었다. 이 두
번째 왕복의 카드사 최종 취소 반영은 별도 조회하지 않았다. 계정·카드·쿠키·
PNR·원문 응답은 출력하거나 저장하지 않았다.

재현용 무원문 출력 스크립트는 `scripts/retry_unprotected_live.py`와
`scripts/retry_delivery_roundtrip.py`에 있다. 두 번째 스크립트는 기존
실결제 운영자의 결제 상한·예약 금액 대조·즉시 환불 절차를 재사용하며
카드와 로그인 정보를 메모리에서만 입력받는다. 재사용 실행에는
`KORAIL_MOBILE_API_LIVE=1`, `KORAIL_LIVE_MUTATION=1`,
`KORAIL_LIVE_REAL_CHARGE=1` 세 스위치가 필요하다. 이 실행 당시에는 스크립트가
앞의 것을 스스로 켜고 PNR 을 가려 출력했으나 지금은 둘 다 고쳤다
(`scripts/README.md`).

영수증 호출은 4자리 또는 8자리 ASCII 원표일자를 상세 응답에서 그대로 받도록
고쳤고, APK의 선택 `txtIndex` 필드를 비어 있지 않을 때만 보내도록 추가했다.
이번 성공 상세에는 `txtIndex`가 없었으므로 그 필드가 과거 실패의 원인이었는지는
검증하지 않았다. 관련 오프라인 읽기 계약 테스트 122개가 통과했다.

위의 `FAIL`은 호출·응답 분류를 실서버에서 확인한 결과다. 입력 조건, 계정 자격,
과거 승차권의 상태가 원인일 수 있으므로 해당 코드만으로 7.0.6 구현 오류나
서버 경로 폐기를 단정하지 않는다. 최신 APK에서 보호된 Device·Version·Key,
호스트, 일부 직렬화 기본값과 DynaPath 본문 오류 필드는 계속 미확인이다.
Android KeyStore·Room·BiometricPrompt·FCM 호스트 실행과 제휴사 실호스트
호출도 이번 Python 실서버 검증 범위에 없었다.

## 재대조 수정의 실서버 확인 — 2026-09-16

7.0.6 디컴파일본과 1:1로 다시 대조해 고친 것 가운데 서버 동작으로 확인할 수 있는
것을 보냈다. 로그인 없이 되는 조회를 먼저 확인했다. 요청 간격은 2초 이상이었고
변경 요청은 보내지 않았다. 원문 응답·쿠키·계정 정보는 출력하거나 저장하지 않았다.

**`strResult` 누락 판정.** 익명 조회 10개의 응답을 HTTP 계층에서 기록했다.
`strResult`가 없던 응답은 네 개였고, 새 규칙에서도 모두 정상 파싱됐다.

- 캐시 파일 `prdMobilePlusMain.cache`(앱 데이터·공지 두 호출)
- 제외 목록의 `common.stationinfo`·`common.stationdata`

나머지 `MobileService.cache`, `schedule.runDt`, `ScheduleView`, `copt.gdMenuLt.do`,
`common.specificDateData.do`는 `strResult`를 실었다. V7
`postSpecificDateData`는 `h_msg_cd` 없이 `SUCC`로 와서 `V7Response`로 돌아왔다.
`ScheduleViewSpecial`은 이전과 같은 `FAIL/ERT900011`이었다.

**리무진 일정의 `trnGpCd`.** `common.code.do`의 `app.limousine.stationCd`/
`app.limousine.stationNm`은 광명역(`0501`)·인천공항T1(`0921`)·
인천공항T2(`0923`)·송도국제교(`0924`) 넷이었다. 광명역→인천공항T1의 다음 날
일정을 같은 폼으로 세 번 보냈다. 키를 빼고, `trnGpCd=999`로, `tmGpCd=999`로
보냈는데, 셋 다 `SUCC/IRG000000`에 같은 42편이었다. 뒤의 두 요청은 검증
스크립트가 필드 검사를 우회해 보낸 것이다(읽기 라우트).

서버가 이 입력으로 일정을 거르지 않으므로, 요청 키 이름은 서버 동작으로 가를 수
없다. 대신 응답의 각 행이 `trnGpCd="980"`을 싣고 있으므로 서버 쪽 필드 이름도
`trnGpCd`다. 값 `980`의 길이는 7.0.6 `ScdlQryIn` 기본값 암호문 길이(3바이트)와
맞는다. 같은 입력으로 부른 `get_limousine_schedules(service_code="980")`는
42편을 모두 파싱해 편 번호·열차 분류(`98`)·운행 순번까지 채웠다. 이 메서드의 첫
실서버 확인이다.

**로그인과 로그인 뒤 조회.** 사용자 계정으로 한 번 로그인했다.
`common.code.do`는 `pwdAESCphd=Y`와 `key`·`idx`를 모두 줬고, 로그인은
`SUCC/IRZ000001`이었다. 이 계정은 느슨하게 바꾼 분기를 타지 않았다. 그 분기는
플래그가 `Y`/`N`이 아니거나 `idx`가 없을 때 쓰인다. 그래서 새 코드가 정상 경로를
막지 않는다는 것까지만 확인했다.

로그인 경로(`MobileService.cache`·`common.code.do`·`login.Login`)와 로그인 뒤
조회는 모두 `strResult`를 실었고 새 규칙에서 정상 처리됐다. 로그인 뒤 조회는
`ReservationView`, `MyTicketNewList.do`, `product.ReservationList`,
`CouponView`, `DelayDiscountView`, `Logout`이다.

**예약대기의 `txtStndFlg` — 실제 버그를 찾았다.** 이 값이 STANDBY·MERGE 요청에서
7.0.6과 어긋날 수 있다는 지적을 예약 두 건으로 확인했다. 결제는 하지 않았고 두 건
모두 만든 즉시 취소했으며, 앞뒤로 계정 예약이 0건인 것을 확인했다.

먼저 조회 12구간 60행을 훑어 예약대기가 열린 행(`h_wait_rsv_flg=" 9"`)을 찾았다.
2026-09-25 서울→부산 041편이고 `h_gen_rsv_cd="13"`(매진),
`h_stnd_rsv_cd="01"`이었다. 같은 열차에 `txtStndFlg`만 바꿔 `1102`(예약대기)를 두
번 보냈다.

| 보낸 값 | 응답 | 서버가 만든 것 |
| --- | --- | --- |
| `"N"`(라이브러리가 이 행에서 계산한 값) | `SUCC`/`IRR000014` "예약대기 가능합니다." | 예약대기. 좌석 1, 입석 0, 운임·결제 기한 없음 |
| `"Y"` | `SUCC`/`IRR000018` "결제하지 않으면 예약이 취소됩니다." | 입석 승차권 예약. `h_seat_no="입석"`, 입석 1, 54,400원, 결제 기한 있음 |

`txtStndFlg="Y"`는 서버에 "입석을 사겠다"는 뜻이다. 예약대기 요청에 실리면 대기가
아니라 결제 기한이 붙은 입석 예약이 만들어진다. 기존 규칙은 매진이고 입석이 열린
행(`h_gen_rsv_cd="13"` + `h_stnd_rsv_cd="11"`)에서 `"Y"`를 보냈으므로, 그런 행에
예약대기를 걸면 호출자가 원하지 않은 입석 예약을 받게 된다. 이제 `1102`는
`txtStndFlg`를 `"N"`으로 박는다. 7.0.6이 STAND 상태에서만 이 값을 채운다는 정적
근거(`TrainScheduleViewModel.java:2870`)와도 맞는다.

병합(`1202`)은 확인하지 못했다. 훑은 60행 중 라이브러리 기준으로 병합 가능한 행이
하나도 없었다. 또 7.0.6 `SeatHelper.isMixedSeat`는 6.5.0과 달리 `h_yms_apl_flg`가
아니라 입석 코드를 인자로 받고 보호된 한 글자 상수와 비교한다. 이번 조회에서 이
필드는 `Y`/`N`으로 왔고, 라이브러리가 아는 6.5.0 값은 `A`/`G`다. 병합 판정 규칙
자체가 7.0.6에서 달라졌을 수 있다.

**지연할인 조회의 `h_page_no`.** 같은 세션에서 `DelayDiscountView`를 네 가지로
보냈다. 라이브러리의 `h_page_no=날짜`, 옛 키 `dptDtTo=날짜`, 키 없음,
`h_page_no=1`이다. 넷 다 `h_msg_cd` 없는 `SUCC`였고 목록이 없었다. 이 계정에는
지연할인권이 없으므로 전송 키는 여전히 서버 동작으로 가려지지 않았다. 뒤의 세
요청은 필드 검사를 우회해 보낸 것이다(읽기 라우트).

### 이번 회차에서 확인할 수 없는 것

아래는 요청을 더 보낸다고 풀리지 않는다. 필요한 조건이 계정이나 서버 쪽에
없거나, 애초에 서버 동작으로 답할 수 있는 질문이 아니다.

| 항목 | 왜 확인할 수 없나 | 확인하려면 |
| --- | --- | --- |
| 지연할인 전송 키 `h_page_no` | 이 계정에 지연할인권이 없어 네 가지 키 조합이 모두 같은 빈 `SUCC`다. 서버가 키를 읽는지 알 수 없다 | 지연할인권을 가진 계정 |
| 로그인 암호화 메타데이터의 느슨해진 분기 | 이 분기는 `pwdAESCphd`가 `Y`/`N`이 아니거나 `idx`가 없을 때만 탄다. 서버는 셋을 모두 정상으로 준다 | 서버가 다른 값을 주는 상태, 또는 앱 실행 관찰 |
| 병합(`1202`)의 `txtStndFlg` | 12구간 60행에 라이브러리 기준 병합 가능한 행이 하나도 없어 예약 자체를 만들 수 없다 | 병합 가능한 행이 뜨는 시점 |
| 7.0.6의 병합 판정 규칙 | `SeatHelper.isMixedSeat`가 입석 코드를 보호된 한 글자 상수와 비교한다. 상수를 복호화할 수 없다 | 앱 실행 관찰 또는 값이 드러나는 응답 |
| 직렬화 기본값 전송 여부(`Lang`, 일부 `Device`/`Version`, 로그인 `custId`·`etrPath`) | 앱이 무엇을 보내는지의 문제다. 서버가 받아 준다고 답이 되지 않는다 | 앱 트래픽 캡처 |
| 보호된 상수(Base64 플래그, `hiduserYn`, 자유석 폼 값 등) | 위와 같다. 값 자체가 암호화돼 있다 | 앱 트래픽 캡처 또는 런타임 후킹 |

# KORAIL Talk 7.0.6 기존 호출 계약 갱신

이 기록은 7.0.6 APK의 Retrofit 선언, 입력·출력 모델과 Python 클라이언트를 정적으로 대조한 결과다. 서버에 요청을 보내지 않았다. 앱이 선언한 계약과 Python 요청을 맞췄다는 뜻이며 서버가 이전 메서드나 별칭을 거부하는지는 확인되지 않았다. 기존 6.5.0 라이브 실행 기록은 [verification-record.md](verification-record.md)에 날짜별 근거로 남겨 둔다.

기존 공개 호출에서 **같은 경로의 HTTP 동사 14개**를 바꿨다. 아래 경로는 `GET → POST`이며 폼 입력이 있는 호출은 질의값을 폼 본문으로 옮겼다.

| 경로 | 7.0.6 입력 |
| --- | --- |
| `login.Logout` | 공통 입력과 `timeStamp`; 로컬 세션은 실패해도 정리 |
| `common.stationinfo`, `common.stationdata` | 인자·본문·폼 Content-Type 없는 빈 POST |
| `schedule.runDt` | `timeStamp` 폼 |
| `push.crwCallRq.do` | 조회 구분 폼 |
| `reservation.ReservationView` | 공통 입력과 앱 화면이 지정한 `timeStamp=0` |
| `certification.ReservationList` | PNR 조회 입력의 POST 오버로드 |
| `research.dcntCrdScheduleView.do`, `ticket.dcntCrdUseQry.do` | N카드 일정·이력 조회 폼 |
| `reservation.dcntCrdExtn.do` | 연장 변경 폼; 기존 동의·dry-run 검사 유지 |
| `ebizcross/getUUID.do` | 인자·본문·폼 Content-Type 없는 빈 POST |
| `file/CACHE/MobileService.cache`, `file/CACHE/prdMobilePlusMain.cache` | `timeStamp` 폼; 서비스 상태의 로그인 사전 조회에도 적용 |

`reservation.tripChgDate.do` 한 경로는 반대로 **POST → GET**이므로 변경 가능 날짜 입력을 질의값으로 옮겼다. 위 차이의 Retrofit 근거는 [7.0.6 비교 기록의 route 표](../analysis/reports/7.0.6-compare/route-surface.md)에 경로별 smali 파일·줄로 기록돼 있다.

승차권 목록은 `myTicket.MyTicketNewList.do`로 옮기고 응답의 `pnr_list` 예약 행 안에 `ticket_list` 승차권 행이 들어오는 구조로 파싱한다. 이 둘은 앱 객체의 camelCase 속성명이 아닌 실제 `@SerialName` wire 키다. 열차 검색에는 성인·어린이·경로·장애 유형별 인원과 선택 좌석 속성을 실으며, 좌석 차량 조회에 출발시각 `txtDptTm`, 운임 조회에 구간 수 `trnCnt`를 싣는다. 승차권 상세 입력은 `txtIndex`를 선택적으로 받고, 상품 상세 예약 순번도 생략할 수 있다. MAAS·여행 메뉴에는 `timeStamp`를 추가했다. 메인 캐시의 중첩 `notice`와 누락 가능한 공통 응답 메시지 필드를 읽고, 환불 결과의 `stlList` 정산 수단 코드를 보존한다. 예약 대기 연락처는 앱과 같은 ASCII 숫자 11자리로 검사한다.

보호된 앱 코드가 정하는 값은 아직 미확인이다. 7.0.6의 Device·Version·Key, 호스트, AES, DynaPath 헤더·키·본문 오류 코드 필드, `RunDateIn`과 메뉴의 정확한 timestamp 산출 함수, `CommonIn.lang` 직렬화 기본값, 메인 캐시 `srtCheckYn`의 기본 문자열·`encodeDefaults`, 리무진 `ScdlQryIn.trnGpCd`의 최종 보호된 wire 키를 임의로 바꾸지 않았다. Python의 밀리초 timestamp는 확인된 타입과 앱의 현재시각 생성 경로에 맞춘 **근사값**이며 앱의 보호된 산출 함수와 동일하다고 주장하지 않는다. 공통 응답의 `strResult` 기본값도 보호돼 있어 타입 조회 파서는 해당 키가 누락되면 성공을 추정하지 않는다.

NetFunnel의 `303` 성공 분류는 7.0.6 SDK의 `isSuccess()` 분기에 맞췄다. 키 없는 `303`도 SDK처럼 통과·완료하며, 완료(`5004`) 호출은 응답 본문을 해석하지 않고 전송 오류만 노출한다. 별도 진단 파서는 서버의 `503` 같은 본문을 계속 판별할 수 있다. 키 없는 `303`의 실제 서버 응답 관측 여부와 DynaPath 본문 오류 필드는 미확인이다.

이 문서는 기존 공개 호출의 변경을 설명한다. 신규 117개 원시 호출과 과거 경로 5개의 정리는 각각 [추가 기록](7.0.6-additions.md), [제거 기록](7.0.6-removals.md)에 둔다. 현재 고수준 클라이언트의 조회·로그인 경계는 56쌍, 변경 경계는 9쌍이며 변경 호출의 명시적 동의·dry-run과 origin 제한은 유지한다. 이후 일부 호출의 실서버 결과는 [7.0.6 실서버 검증](7.0.6-live-verification.md)에 기록했다.

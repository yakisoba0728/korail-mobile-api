# KORAIL Fixed-RT DynaPath Design

**Status:** Implemented and bounded-live-verified on 2026-07-13

## Context

The repository currently contains two DynaPath generation paths. The normal
client path uses SDK version `v1.0.3` and maintains a rolling list of request
time deltas, while the successful KORAIL probe and the supplied reference
implementation use SDK version `v1` and emit exactly one `rt=0` field for every
token. Maintaining both paths makes live behavior depend on an implementation
that has not matched the successful reference request.

This design supersedes the stateful DynaPath requirements in the earlier public
API stabilization and cache-read expansion documents.

## Decision

Replace the stateful implementation completely with one canonical fixed-RT
engine. The successful probe implementation becomes the normal
`generate_dynapath_token()` behavior. There will be no rolling-delta mode,
compatibility switch, probe-only generator, or probe-only provider.

Alternatives considered and rejected:

- Changing only live configuration would leave the incorrect stateful public
  path and duplicate token algorithms in place.
- Keeping the stateful engine behind an option would preserve ambiguity that
  the user explicitly chose to remove.
- Keeping probe aliases would retain two names for the same behavior without a
  supported compatibility requirement.

## Canonical Token Contract

The default and live generator configuration will use the supplied reference
contract:

- application id `com.korail.talk`;
- OS type `Android`;
- SDK version `v1`;
- four random characters drawn from uppercase ASCII letters and digits;
- one literal `rt=0` field per payload;
- the existing KORAIL encoding table, prefix, key derivation, and body encoding;
- caller-supplied device id, app-start timestamp, OS version, and device model;
- the raw application-signature setting
  `[38ff229cb34c7dda8e28220a2d750cce]`, serialized as
  `%5B38ff229cb34c7dda8e28220a2d750cce%5D` in the assembled payload.

The payload field order remains:

`ai`, `di`, `as`, `su`, `dbg`, `emu`, `hk`, `it`, `ts`, `rt`, `os`, `dm`,
`st`, `sv`.

The default security-state fields `su`, `dbg`, `emu`, and `hk` remain `false`,
as in the reference implementation. Existing identity and encoding settings
remain available; only the request-history input is removed so callers cannot
restore rolling or nonzero `rt` behavior. Regardless of other caller-supplied
settings, every generated payload contains exactly one literal `rt=0` field.

## Components and Data Flow

`DynapathTokenSettings` remains the configuration boundary for runtime device
identity. It validates the five required runtime values but no longer exposes
`recent_request_deltas`.

`generate_dynapath_token(settings, timestamp_ms, random_text)` assembles and
encodes the canonical fixed-RT payload. `DynapathTokenGenerator` remains a
small callable adapter so the HTTP client can inject timestamp and random
providers in deterministic tests, but it owns no request history.

`KorailHttpClient` continues to create one adapter when token settings are
configured and attaches its result only to the exact existing DynaPath
allowlist. A custom `token_provider` remains supported as the mutually
exclusive alternative configuration source.

`build_config_from_env()` continues to require real device identity values and
captures one app-start timestamp. Its defaults change to SDK version `v1` and
retain the raw signature setting that the canonical serializer encodes once;
it does not use probe device identifiers.

The probe-only function, provider class, constants, and package exports are
removed because their implementation is now the sole standard engine.

## Error Handling

Required DynaPath identity values continue to fail during configuration with a
`ValueError`. Token-generation failures continue to be wrapped by the HTTP
layer as `KorailProtocolError`. Exact-path allowlisting and DynaPath-specific
403 response classification remain unchanged.

No ticket lookup is added. Ticket-list retrieval is independent of token
construction and is not needed to validate this replacement.

## Testing

The implementation will follow a red-green cycle:

1. Replace stateful expectations with an exact known token vector generated by
   the successful fixed-RT contract.
2. Prove repeated requests use independent timestamps/random text while both
   payloads contain only `rt=0` behavior.
3. Prove HTTP header generation uses unchanged settings across consecutive
   requests and never exposes rolling state.
4. Prove live environment configuration selects SDK version `v1` and the raw
   signature value that is encoded exactly once during payload serialization.
5. Remove probe export expectations and update current README/progress wording.
6. Run the focused DynaPath/live/HTTP/readme tests, then the complete test suite.

Live network smoke tests remain opt-in because they require credentials and
real device environment values. The deterministic known token vector is the
offline acceptance criterion for the generation algorithm.

## Scope

In scope are the DynaPath implementation, its HTTP/live wiring, package
exports, direct tests, and current user-facing documentation. Historical
design and plan documents are not rewritten; this document explicitly
supersedes their stateful requirements. Reservation, payment, ticket mutation,
NetFunnel, Sid generation, and unrelated read APIs are out of scope.

# 실서버 확인 현황

메서드 제공, 오프라인 테스트 통과, 실서버 성공은 서로 다른 확인 범위입니다. 현재 공개 메서드는 83개입니다.
이 문서는 3.0.0의 확인 범위를 설명합니다. `3.0.0.dev0` 개발 wheel의 실서버 성공 관측은 익명 서울→부산 직통 첫 페이지 조회 1회뿐이며 출시된 3.0.0 배포 파일의 실서버 검증은 아닙니다([기록](records.md#live-check-300-dev0-20261023)). 그 밖의 아래 실서버 결과는 2.x 시기 코드의 기록입니다.
날짜별 원래 기록은 [날짜별 실서버 기록](records.md)과 각 검증 문서에 당시 이름·버전·집계 그대로 있습니다.

## 현재 상태 (2026-10-24) {#current}

- 2026-10-21부터 익명 열차 조회를 포함한 모든 요청이 `-8204`("원활한 예매 및 결제 서비스를 위해 최신 버전으로 업데이트해 주세요")로 실패한다는 사용자 보고가 있습니다([#32](https://github.com/yakisoba0728/korail-mobile-api/issues/32)).
  `2!` 기본 헤더 도입 전 `main`(1b89779)에서 기본 `AppVersion` 7.0.8과 `app_version="7.0.10"`만 바꾼 설정(API `Version` 250601003) 모두 실패했습니다.
- 2026-10-23 08:16 KST, 소유자 허락을 받아 PyPI의 2.6.2로 로그인 없는 직통 열차 조회를 한 번씩 했습니다.
  기본 조합(`2!`·`AppVersion=7.0.8`·API `Version=250601003`)과 `AppVersion=7.0.10`·API `Version=250722001` 모두 `SUCC`/`IRG000000`이었습니다([기록](records.md#live-check-262)).
  보고된 실패가 `2!` 헤더 도입 전 코드였으므로 버전보다 `2!` 헤더가 차이를 만든 것으로 보이지만, 확인한 범위는 익명 조회 한 노선뿐입니다.
- 2026-10-23 23:34:34 KST, `3.0.0.dev0` 개발 wheel의 기본 요청 버전으로 익명 서울→부산 조회(2026-10-24 09:00 이후, 일반 직통 첫 페이지)를 한 번 실행해 `SUCC`/`IRG000000`, 열차 10개를 받았습니다([입력·커밋·관측 한계](records.md#live-check-300-dev0-20261023)). API 전송 인계 1회·대기열 전송 인계 2회이며, 정확한 HTTP 상태와 대기열 반납 성공은 미관측입니다.
  이 개발 wheel의 한 노선·날짜·시각만 확인했으며 출시된 3.0.0의 호환 보증이 아닙니다. 3.0의 로그인·인증 조회·예약·취소·결제·환불은 실서버 미검증입니다.
- 2.6.2와 3.0은 기본 버전을 바꾸지 않습니다. 그 전의 기록은 2026-10-23 병합 전 작업 트리의 7.0.10·250722001·`2!` 관측 1회입니다([조건과 한계](verification-7010.md#diagnostic-20261023)).
- 현재 `-8204`는 로그인과 실패를 예외로 분류하는 경로에서 `KorailAppUpdateRequiredError`(`KorailAppError`의 하위 예외)이며 서버 메시지를 보존합니다. 카드 결제·도우미석 안내처럼 FAIL 모델을 반환하는 경로는 결과 필드를 확인해야 합니다([오류 처리](guide/errors.md#app-update)).
  `-8204`는 앱 리터럴이 아니라 #32에서 관측된 서버 코드입니다. 이 오류 분류의 회귀 검사는 합성 응답과 소켓 차단 환경에서 했으며, 위 익명 조회 성공이 다른 경로의 검증을 대신하지 않습니다.
